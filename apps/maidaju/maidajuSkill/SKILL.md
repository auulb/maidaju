# 麦当劳多人点餐方案（McD Feast Planner）

把「N 人、¥B、若干忌口」变成 **三套可点单的组合**，而不是随口报几个汉堡。

## 输出契约

一次交付必须包含：

1. **三套方案，固定三种取向**：
   - 🎲 **多元体验**：单品数/品类数最多，重复最少
   - 💪 **健身活力**：蛋白质与蛋白密度最高，热量/脂肪受控，饮品优先无糖
   - ⚡ **能量满格**：同样预算内总热量最高，主食管够
2. 每套都给：总价、人均、总热量、人均热量、蛋白质、结构（主食/小食/饮品/甜品的份数）、逐品清单、忌口分配、≈ 估算标记。
3. **如果用户给了成员名单**，每套再加「逐人餐盘」：谁拿哪份主食/饮品、共享小食、个人分摊与个人预算是否够。
4. 必须说明计价口径（见下）。
4. 结尾只推进到「选 A/B/C → 用 `calculate-price` 复核」，**默认不进入支付、不创建订单**。

## 快速开始

```bash
# 用户: 8 个人、300 块、两人不吃辣、一人喝无糖
python3 scripts/plan.py --people 8 --budget 300 --no-spicy 2 --no-sugar 1 \
    --city 上海市 --keyword 人民广场
```

```bash
# 有成员名单时，输出逐人餐盘（可带个人预算）
python3 scripts/plan.py --budget 220 --store 1450713     --member '小王:no-spicy,budget=50' --member '小李:no-sugar,budget=50'     --member 小张 --member 小赵 --member 小钱 --member 小孙

# 已确定门店 / 外送 / 复核价格
python3 scripts/plan.py --people 8 --budget 300 --store 1450713
python3 scripts/plan.py --people 8 --budget 300 --address-id 123456 --be-type 2 --order-type 2
python3 scripts/plan.py ... --verify --json /tmp/plan.json

# 团餐（企业团餐）：自动选满折档位 + 助餐服务，按活动后实付规划
python3 scripts/plan.py --people 8 --budget 300 --be-type 6 --order-type 2 \
    --address-id 123456 --no-spicy 2 --no-sugar 1 --verify
```

脚本自检（离线；自带 `data/fixtures/` 门店快照）：

```bash
python3 scripts/selftest.py
```

`scripts/` 相对本 skill 目录；在 skill 目录下直接运行即可。首次运行会拉菜单与每个餐品详情（约 1 分钟），之后走 `data/cache/`（菜单 30 分钟、详情 24 小时）。

## 工作流

### 0. 先把参数补齐

| 参数 | 处理 |
|---|---|
| 人数、总预算 | 缺就必须问；不要猜 |
| 不吃辣 / 要无糖 | “有人…”→ 先按 1 人算，并在输出里注明可改人数重跑；能问清就问 |
| 不吃牛肉/猪肉/海鲜、素食 | 可选，`--no-beef/--no-pork/--no-seafood/--veg` |
| 门店 | 优先问“哪家店/哪个地标”；也可先给最近门店再让用户确认 |
| 到店 / 外送 / 得来速 / 团餐 | 默认到店自取（`--be-type 1 --order-type 1`） |
| 成员名单 | 可选。想输出「谁吃哪份」时问一句“要不要按人分？”；名字 + 忌口 + 个人预算，`--member '小王:no-spicy,budget=35'` 可重复 |

一次最多问 3 个问题。能合理默认的（如“有人不吃辣”→1 人）先默认再声明。

### 1. 选门店（MCP）

- 到店自取：`query-nearby-stores`（`beType=1, searchType=2, city, keyword`）
- 得来速：`query-nearby-stores`（`beType=5`，后续所有调用都要带 `beCode`）
- 麦乐送/团餐：`delivery-query-addresses` → `delivery-query-stores`（`beType=2/6`）

`plan.py` 会在没给 `--store` 时自动做这一步，并列出前 3 家备选门店。

### 2. 跑三套方案

```bash
python3 scripts/plan.py --people <N> --budget <B> [忌口参数] --store <storeCode>
```

脚本内部：

1. `query-meals` 拉门店菜单 → `query-meal-detail` 展开套餐默认搭配、饮料规格与 `diffPrice`；
2. 用 `list-nutrition-foods` + 官网营养计算器快照匹配营养（匹配不到 → 角色中位数估算并标 ≈）；
3. 用带约束的贪心 + 模拟退火 + 局部搜索求三套方案；
4. 输出 markdown（可直接贴给用户）和 `--json` 机器可读结果。

### 3. 呈现给用户

- 先给 3 行对比表（总价/人均/热量/蛋白/蛋白密度/单品数），再展开 3 张方案卡。
- 把“≈”解释清楚：官方营养表未收录的新品，数值为估算。
- 主动点出忌口怎么分：辣味主食几份、给不吃辣的人留几份不辣；无糖饮品几份。
- 有成员名单时，把「逐人餐盘」放在每套方案的单品表后面；先报“主食 6/6、饮品 6/6、冲突 N 条”，再展开表格。
- 个人预算不够时不要偷偷降级：照实说“小王分摊 ¥50.2，超 ¥0.2”，并给两个选项——加个人预算，或少点共享小食。
- 结尾只问「选 A / B / C」，或「要更便宜 / 更辣 / 更多无糖」。

### 4. 用户选好后复核价格

```bash
# 方案已含 order_items（productCode + roundList），可直接算价
python3 scripts/plan.py ... --verify
```

或直接调用 `calculate-price`（`orderType/beType/beCode` 与建单一致）。把「计划价 vs 门店价」的差值告诉用户；有差异以门店为准，并说明可能是套餐/促销差异。

## 团餐 / 外送：把活动价算进预算

团餐的菜单价 ≠ 实付：整单满额会触发 78折/74折…，还会加配送与打包费。脚本已内置这层：

1. `query-meal-assistance` 取可用助餐服务（GMS001 保鲜速达 / GMS002 专人分餐 / GMS003 专人摆台）；
2. `query-promotions` 取每家服务对应的满折/满减阶梯（`discount=26` → 74 折；`type=2` 商品不参与）；
3. 选出「同预算能买到最多菜」的服务 + 档位，把商品价按折扣缩放后再求解；
4. 用一次 `calculate-price` 探测配送/打包费，最后再对三套方案逐一算价复核。

因为阶梯是跳变的（¥499 全价 vs ¥500×0.78），预算要按**实付**算。脚本会主动跨过档位：300 元预算可以点到 ¥365~380 的菜单价。

用法：

```bash
# 团餐（需要配送地址；地址可先用 MCP delivery-query-addresses 查）
python3 scripts/plan.py --people 8 --budget 300 --address-id <addressId> \
    --be-type 6 --order-type 2 --verify

# 指定助餐服务 / 关掉活动（按菜单价对比）
python3 scripts/plan.py ... --be-type 6 --gm-service GMS002
python3 scripts/plan.py ... --be-type 6 --no-promo
```

输出必须交代四件事：**原价、活动优惠、配送/打包费、实付**；并注明档位（如「满 ¥300 打 7.8 折」）、助餐服务名，以及「再点 ¥X 可到下一档」。

口径与坑：

- 活动是**整单满额**，不是每份打折；预算按实付而不是菜单价。
- `type=2` 的商品（多为随心配/特殊套餐）不参与活动，脚本按原价计并在方案里列出。
- 不同助餐服务的折扣不同，且部分服务只支持 07:00–20:00 送达（`enable=false` 不参与选择）。
- 团餐菜单价普遍高于到店（同一汉堡可能 ¥15 vs ¥14），换模式必须重跑。
- 配送（通常 ¥6）与打包费（¥3–9）为门店估算值，`--verify` 以算价接口为准。
- 满减（`promotionType=31`）同样支持；阶梯从 `reduceInfo` 读取。

### 5. 只有用户明确要下单时

再走 `create-order`。本 skill 的默认终点是「算价复核」。

## 逐人餐盘（`--member`）

给了成员名单后，脚本会把每套方案的购买数量拆到「人」：

- 每人 1 份主食 + 1 份饮品；主食按该成员自己的忌口筛（不吃辣、不吃牛/猪/海鲜、素食），饮品按无糖要求筛。
- 分配用二分图最大匹配（不是“先到先得”），所以不吃辣的人不会被没有忌口的人抢走唯一的不辣主食。
- 套餐可以被拆开分给不同人；脚本会优先让主食和同套餐里的饮料落到同一个人，其次才跨套餐拆。
- 小食、甜品和富余份数进「共享池」，成本按人数均摊；这个分摊是本局记账，**不是**门店逐人收费。
- 个人预算 = 主食分摊 + 饮品分摊 + 共享人均。超了就如实报冲突；只会尝试换更便宜的同角色餐品，不会偷偷删掉某人的主食。
- 每人预算都给了且合计小于总预算时，求解器直接按「个人预算合计」当总预算，避免一开始就注定有人超。

局限：这是**分配启发式**，不是门店的真实分单；订单仍是合并后的 `order_items`。共享小食里有辣味时，只能提示“留给能吃辣的人”，不能按人隔离。

## 计价与营养口径（必须向用户交代）

- **价格 = 当前门店/时段的菜单价**，再按模式折算：
  - 到店/得来速：无配送费，`实付 = 菜单价`；
  - 麦乐送：`实付 = 菜单价 + 配送费 + 打包费`（脚本用一次算价探测）；
  - 团餐：`实付 = 菜单价 − 整单满折/满减 + 配送/打包费`，折扣按所选助餐服务与档位，`type=2` 的商品不参与活动（详见「团餐 / 外送」）。
- 标注「随单购麦金卡优惠 / 随单购早餐卡优惠」的套餐按**原价**计入预算——因为它要求额外买卡，脚本已如此处理。
- **套餐按默认搭配**计价；「饮料换无糖」按详情里的 `diffPrice` 加价。用户下单时可再换同价项。
- **营养来源**：MCP `list-nutrition-foods` + 麦当劳中国官网营养计算器（详见 `references/data-sources.md`）。
  - 组合餐营养 = 各子项之和；
  - 两者都没有的单品（多为当季新品）标 **≈**，用同类中位数或人工估算，**不要**当成官方数据。
- **糖/油口径**：官方营养表没有「添加糖」字段，所以「少糖」用 **含糖饮品份数 + 碳水** 代理，「少油」用脂肪克数；无糖饮品按商品名（无糖可乐/纯悦/美式/鲜萃/红茶）判定，不是实验室检测值。
- **结构底线**：每人 1 主食 + 1 饮品；小食/甜品按剩余预算铺。
- **忌口规则**：辣味主食 ≤ 人数 − 不吃辣人数；含糖饮品 ≤ 人数 − 无糖人数，且无糖饮品 ≥ 无糖人数。

## 三套方案的目标函数

| 方案 | 目标 | 主要约束 |
|---|---|---|
| 多元体验 | 单品数 ×60 + 品类数 ×14 + 份数 ×3 + 甜品种类 ×6 − 重复惩罚 | 预算、主食/饮品份数、忌口；人均热量软上限 820 kcal |
| 健身活力 | 蛋白 ×9 − 脂肪 ×1.6 − 碳水 ×1.0 + 无糖饮品 ×4 + 单品数 ×12 | 人均热量 ≤700 kcal、脂肪 ≤28 g（软惩罚），无糖优先 |
| 能量满格 | 总热量 ×1 + 蛋白 ×3 + 品类数 ×10 | 总热量软上限 1000 kcal/人，主食/饮品份数 |

搜索是启发式（固定随机种子，结果可复现），**不承诺全局最优**；`selftest.py` 会校验三套方案都满足硬约束、预算、忌口，并保持三种取向的差异。

## 降级方案：脚本跑不了但 MCP 工具可用

按顺序手工做，结论一样要落在三套方案上：

1. `query-nearby-stores` 拿 `storeCode`；
2. `query-meals` 拿分类与价格；
3. 对候选套餐 `query-meal-detail`，读 `rounds[].choices[].isDefault / diffPrice` 还原默认搭配与换无糖差价；
4. `list-nutrition-foods` 按名称匹配营养（去空格/括号/“杯”字后匹配；`中薯条`、`可乐中杯`、`无糖可口可乐中杯` 这种带规格名最准）；
5. 按上面的目标函数和忌口规则手搭三套；每套用 `calculate-price` 复核总额；
6. 呈现时同样标注：默认搭配、≈ 估算、价格为门店价。

匹配不到营养的餐品：优先换掉；确实想保留就标 ≈，并在结尾说明。

## 常见坑

- **门店不同价格不同**：换店必须重跑，不要复用上一家店的价格。
- **“随单购”套餐**：页面现价是买卡后的价，直接当预算会低估一倍。
- **1+1 随心配**这类超值组合会被算法优先选中：便宜且蛋白高，但会让清单显得单一。想更“丰盛”可 `--exclude 随心配` 重跑。
- **“任选/随心选”套餐**：脚本取页面默认搭配；用户想自选时，按 `query-meal-detail` 的选项替换并重新 `calculate-price`。
- **辣度**靠菜名（辣/龙焰/椒麻）+ `data/flags.json` 人工覆盖判断，不是官方辣度分级；对严格忌辣的用户，建议在方案里额外留 1-2 份不辣主食冗余。
- **过敏原/宗教饮食**（花生、清真等）不能靠菜名可靠判断：必须提示用户向门店确认，不要给保证。
- **逐人餐盘是分配视图**：同一份套餐可以被拆给两个人，也可能出现“你的汉堡来自 A 套餐、饮料来自 B 套餐”。这是为了在现有购买清单内满足每个人的忌口，不是门店真实分装。
- **素食**支持有限（菜单里几乎没有素食主食），`--veg` 无解时会直接显示“未能完全满足”。
